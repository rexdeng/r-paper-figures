1执行摘要

投稿被退回时最常见的描述是「图件分辨率不足」或「尺寸不符」，但真正的成因往往在出图之前就已经埋下：你在 RStudio Plots 面板里看到的图，和你用 ggsave() 写进磁盘的图，是两套独立渲染管线的产物。前者是屏幕设备，后者是文件设备，两者的物理尺寸、像素映射、字体解析路径都不相同。面板里「看着刚好」从来不构成任何合规证据。

核心结论

合规性只能由「物理尺寸 × 分辨率 × 显式声明的字号/线宽」这四元组决定，而这四元组必须在你写代码时就被写死，不能交给窗口大小、默认参数或设备自动推断。做到这一点，预览与最终文件才会真正一致。

四条要点

  1. 预览为什么会骗你：Plots 面板约 96 dpi 逻辑像素、尺寸由窗口决定且随缩放变化（"Auto"），它从不关心你的目标栏宽是 89 mm 还是 190 mm。窗口拉大一点，同样的代码看起来就"字号变小了"——但版式其实一个字都没变。
  2. 正确做法是什么：把画布尺寸单位统一为 mm、字号与线宽统一为 pt、渲染与导出共用同一套文本排版引擎（ragg），再用与导出一致的物理尺寸把 PNG 等比投回屏幕做校对。
  3. 硬规则一 — 尺寸用 mm，显式传参：ggsave() 的 width/height 默认单位是 inch。写 width = 7 得到的是 177.8 mm，不是 180 mm，更不是你以为的"7 厘米"。期刊要 mm，你就写 units = "mm"。
  4. 硬规则二 — 认清两套字号单位：theme() 里 element_text(size =) 的单位是 pt；但 geom_text() / annotate() 的 size 美学单位是 mm。写 size = 8 想表达 8 pt，实际渲染成 8 mm ≈ 22.76 pt，字号直接放大到近 3 倍。正确写法是 size = 8 / .pt（.pt ≈ 2.845276）。
  5. 硬规则三 — 字体必须显式绑定，并禁用 showtext：不写 family 时，sans 在 Windows 上解析为 Arial、在 PDF 设备上解析为 Helvetica、在 ragg 下走 systemfonts 解析。同一份代码在不同设备出不同字宽，直接导致文本溢出或换行位置漂移。
一句话记住

dpi 只改变像素密度，不改变版面比例。字号用 pt、画布用 mm 声明之后，600 dpi 与 150 dpi 渲染出的图，元素相对位置与字号占比完全相同——这条性质正是"预览即所得"能够成立的理论基础。

2.1　设备不同：屏幕设备与文件设备是两套管线

错误现象

Plots 面板里图占满整个面板、字号看着舒服；点 Export 或跑 ggsave() 之后，图变得"空旷"，文字相对变小，或者反过来挤成一团。同一段代码，今天和昨天打开看起来还不一样。

机制解释

RStudio 的 Plots 面板背后是一个屏幕图形设备（png 设备，通常 res = 96），它的物理尺寸由面板的像素大小 ÷ 96 反推得到。ggsave() 则打开一个文件设备（tiff()、agg_tiff()、pdf()），物理尺寸完全来自你传入的 width/height。

关键在于：ggplot 的版面计算依赖「画布物理尺寸 ÷ 字号」，两者同时缩放时版面不变，只缩放其一时比例就崩。面板的 "Auto" 尺寸随窗口拉伸而变，于是你每次看到的都是「同一个主题在不同画布尺寸下的不同结果」。此外，屏幕设备的抗锯齿、字形 hinting 与文件设备不同，细线在屏幕上"看得见"，300 dpi 下可能细到断墨。

正确做法

把「校对」这件事从面板里搬出来：用与导出完全相同的 mm 尺寸渲染一张 PNG，再按物理尺寸等比投回屏幕（见 §5.3）。屏幕上看到的字号占比、留白比例，就是最终印刷的比例。面板只用来做"改代码有没有报错"的粗看，不承担任何合规判断。

2.2　物理尺寸与像素尺寸的混淆

错误现象

ggsave("fig.tif", p, width = 7, height = 5, dpi = 600) 跑得通、文件也生成了，投稿系统却提示 "Figure width exceeds column width"。作者认为 7 是个小数字、"应该差不多"，实际宽度是 177.8 mm——对 89 mm 单栏来说是两倍，对 190 mm 双栏又差了 12 mm。

机制解释

ggsave() 的 width/height 默认单位是 inch（units = c("in", "cm", "mm", "px") 的第一个）。7 in × 25.4 = 177.8 mm。多数期刊规格表用的是 mm，两套单位之间靠心算切换，误差被人为放大。dpi 只决定"每 inch 多少像素"，它与物理尺寸是两个正交维度，两条命令分别设置、互不换算。

更隐蔽的一层：7 in @ 600 dpi = 4200 px。若你把这张 4200 px 的图在 Word 里按 89 mm 宽插入，印刷有效分辨率就变成 4200 ÷ (89/25.4) ≈ 1199 dpi——数值上"足够"，但字号是按 177.8 mm 画布设计的，缩到 89 mm 后原本 7 pt 的字只剩 3.5 pt，直接跌破可读下限。这就是"分辨率达标、字号不合规"的成因。

正确做法

永远显式写单位，且写期刊给的那个数：units = "mm", width = 89, height = 120。把栏宽定义成常量在脚本顶部（W_1COL <- 89），后面所有图引用常量，改刊时只改一处。绝不用 inch 作为科研图的中间单位。

2.3　字号单位错用（最高频错误）

错误现象

主题字号设成 7 pt 一切正常，但图里用 geom_text() 或 annotate() 加的标注"炸"了——字大得像标题，压住数据点、互相重叠，有的干脆跑出画布。作者反复调 theme() 毫无效果，因为问题不在 theme。

机制解释

ggplot2 里存在两套互不相同的字号单位：

  • theme(element_text(size = ))、base_size、pointsize 参数 —— 单位是 pt（排版点）。
  • geom_text(size = )、annotate("text", size = ) 的 size 美学 —— 单位是 mm（字体高度，grid 的 gpar(cex) 派生体系）。

所以 size = 8 的含义是「字高 8 毫米」。换算：8 mm × 2.845276 ≈ 22.76 pt，是期望值 8 pt 的 2.8 倍。反过来，想让标注等于 8 pt，必须传 8 / 2.845276 ≈ 2.81（mm）。这就是为什么"照着主题字号填 geom_text 的 size，图一定崩"——两个 8 的含义差了整整一个数量级。

ggplot2 为此导出了常量 .pt（= 72.27/25.4 = 2.845276，pt 与 mm 的换算因子），标准写法就是 size = 8 / .pt。这个写法自我解释、无需记数字，应作为团队规范固定下来。

正确做法

统一入口：写一个 pt_mm() 辅助函数，凡是要喂给 geom_text()、annotate() 或 linewidth 的值都过一遍。element_text(size =) 则直接写 pt 原值，不要再过转换函数——这是最容易反手犯错的地方。

2.4　线宽单位与 API 迁移

错误现象

想要 1 pt 的坐标轴线，写 linewidth = 1，出来明显偏粗；或者沿用旧脚本里的 size = 0.5，升级 ggplot2 后收到 The `size` argument of `element_line()` is deprecated 警告，且渲染结果与老图不一致。

机制解释

ggplot2 ≥ 3.4 起，element_line()、geom_line() 等改用 linewidth，单位是 mm。所以 linewidth = 1 是 1 mm ≈ 2.83 pt，接近期望值的三倍。换算关系：1 pt = 0.3528 mm（PostScript pt），故 1 pt 线宽应写 1 / .pt = 0.3515。

旧参数 size 在 geom 中曾表示线宽，3.4 之后对线条类 geom 废弃（对 geom_point 它仍是点直径、单位 mm），混用会造成「同一条线在不同图层粗细不同」。期刊对线宽常设下限（如 0.25 pt）与上限（如 1.5 pt），一旦单位错了，不是"略粗"而是直接越界。

另需注意：屏幕上 1 px 的线在 600 dpi 下会被渲染成约 6 px 宽的实线，但若原始线宽低于输出设备的可寻址粒度，抗锯齿会把它摊成灰色虚线感的浅灰线——灰度打印后可能直接消失。所以线宽下限不仅关乎"好看"，关乎"能不能印出来"。

正确做法

一律用 linewidth，值统一过 pt_mm() 换算；轴线 0.5 pt、数据线 1 pt 分别写 pt_mm(0.5)、pt_mm(1)。运行 ggplot2::theme_set() 前先确认包版本，避免旧脚本静默走废弃分支。

2.5　字体未显式绑定（以及 showtext 的隐形破坏）

错误现象

屏幕上是一套字形，导出的 TIFF 里换了一副面孔：字宽变了、α 和 µ 变成了方框、标签从两行变一行或溢出坐标轴。中文图在 Windows 上正常，到合作者 Mac 上全是豆腐块。

机制解释

不写 family 时，ggplot 用默认 sans，而 sans 是一个逻辑别名，由具体设备负责解析：

  • Windows 屏幕设备 → 常解析为 Arial；
  • pdf() 设备 → 解析为 Helvetica（且默认只认 Type1 标准 14 字体，不嵌入系统字体）；
  • ragg → 走 systemfonts + textshaping，按系统字体库匹配。

不同字体的相同字号字宽不同（Arial 与 Helvetica 度量接近但不完全一致，中文黑体与英文无衬线的混排度量差异更大）。ggplot 计算文本包围盒（用于轴标签是否旋转、图例是否换行）时用的是字体度量，一旦导出设备换了字体，包围盒就变了，版面随之漂移。这不是"长得有点像"的问题，是布局重排。

showtext 会接管文本渲染（把文字画成路径/位图），它维护自己的一套字体注册表，与 ragg 的 systemfonts 路径互相冲突：两者同时启用时，预览与导出可能走不同分支，字形与字宽再次分叉。它是"预览不一致"最典型的隐形元凶——尤其在你为了显示中文而随手 showtext_auto() 之后。

正确做法

① 所有文本元素显式写 family = "Arial"（或期刊指定字体），并在脚本里把它设为常量；② 出图前用 systemfonts::match_font("Arial") 验证字体真实存在、路径可读；③ 中文用 systemfonts::register_font() 注册后显式引用；④ 不要加载 showtext，全程交给 ragg。

2.6　dpi 与「有效分辨率」

错误现象

文件属性里明明白白写着 600 dpi，审稿意见却是 "insufficient resolution"。或者：为了"保险"把画布设成 3 倍大小再缩到 300 dpi，自认为分辨率翻了三倍。

机制解释

dpi 是元数据，它只告诉排版软件「这一英寸该铺多少像素」，本身不产生任何像素。真正被审读的是最终印刷尺寸下的有效像素数：

有效 dpi = 像素宽度 ÷ 最终印刷宽度（inch）

"3 倍尺寸出图再缩小"的做法里，像素被重采样或原样塞进更小的物理尺寸，看似提高了 dpi 数值，但字体是按大画布设计的，缩到目标尺寸后字号的物理高度等比例缩水。于是出现"像素够了、字却只有 3 pt"的组合故障——这类图在审读环节被判"不可读"，与分辨率无关。

另一种常见误解：以为改 dpi 参数能"提升清晰度"。在物理尺寸固定的前提下，提高 dpi 确实增加像素（px = mm ÷ 25.4 × dpi），这是有效的；但若同时缩小物理尺寸，等于把像素挤进更小空间，视觉上并不会变清晰。

正确做法

按最终印刷物理尺寸直接出图，一次到位，不做后期缩放。出图后用脚本回读像素尺寸，与理论值对账（mm ÷ 25.4 × dpi），差值超过 1 px 就说明参数没生效（常见于设备不支持 units 而被静默按 inch 处理）。

注意

以上六条会叠加放大。典型翻车链路是：ggsave() 裸调用（inch + 300 dpi + 默认设备）→ 画布偏大 → 为"看清楚"把整体字号调大 → geom_text(size = 8) 再放大 2.8 倍 → 字体被设备替换导致溢出。修一条没用，必须按 §5 的流水线整体替换。

格式选择：TIFF 不总是对的

Nature 对线条图/示意图偏好矢量格式（EPS / PDF / AI），TIFF 主要用于照片类与需要半色调的图像；不少刊明确要求"文字保持可编辑"。若目标期刊写明"不接受 TIFF"，应改用矢量格式（ragg::agg_png 不合适，应用 pdf() 或 svglite）。本文的 TIFF 方案适用于明确接受位图、或组合图必须位图化的场景。稳的做法是：矢量版 + 位图版各交一份，按刊要求提交。

3.1　把规格变成脚本常量

规格表的价值在于"写进代码"，而不是"贴在便签上"。推荐在脚本顶部集中声明，一处改动、全图生效：

# ---- 目标期刊规格（以投稿指南核对后的值为准）----
JOURNAL        <- "Elsevier"
W_1COL         <- 90    # 单栏 mm
W_1_5COL       <- 140   # 1.5 栏 mm
W_2COL         <- 190   # 双栏 mm
H_MAX          <- 250   # 最大高度 mm
FS_BASE        <- 7     # 正文字号 pt
FS_MIN         <- 6     # 最小字号 pt（上下标下限）
LW_AXIS        <- 0.5   # 轴线 pt
LW_DATA        <- 1.0   # 数据线 pt
DPI_LINE       <- 600   # 线条/组合图 dpi
DPI_HALFTONE   <- 300   # 照片/半色调 dpi
FONT_MAIN      <- "Arial"

注意 FS_MIN 与最细线宽这两条下限约束要单独存在：它们不参与"设计"，只参与"校验"。任何低于下限的元素都应该在出图前被脚本拦下来。

4TIFF + LZW 的规范要点

TIFF 是容器格式，规范不写在"TIFF"这三个字母上，而写在压缩方式、位深、色彩空间、背景这四个字段里。期刊退回的图，多半是这四个字段之一不合规，而非格式选错。

4.1　LZW 是无损压缩，放心用

  • LZW（Lempel-Ziv-Welch）是无损算法，解压后像素与未压缩版本逐字节一致，不存在 JPEG 那种振铃/块状伪影。它靠"重复序列建字典"压缩，因此对大面积纯色区域（白背景、填充色块、折线图的空白区）极为有效，对高频细节（噪声、渐变、照片）效果有限。
  • Elsevier 的制图指南明确要求对 TIFF "flatten layers and save with LZW compression"——合并图层 + LZW。合并图层是前提，图层化的 TIFF 在部分排版系统中会被按"第一层"处理，导致元素丢失。
  • 命令层面就是 compression = "lzw"，不要传 "none"（体积暴涨）或 "jpeg"（有损，等于自毁分辨率）。

4.2　位深、色彩空间、背景：三个必查字段

表 4-1　TIFF 关键字段的合规取值
字段合规取值不合规后果与说明
位深 8 位/通道（RGB 共 24 位） 多数期刊按 8 位/通道接收。16 位/通道可被部分刊接受，但体积翻倍，且投稿系统常在上传时静默降位。除非期刊明确要求，默认用 8 位。
色彩模式 RGB（sRGB 色彩空间） R 端只能输出 RGB/sRGB。需要 CMYK 必须在 R 之外转换（Photoshop / ImageMagick）。CMYK 色域比 sRGB 窄，亮荧光色（纯青、纯品红、亮绿）转换后会明显变暗发闷，转换后必须目视复核，必要时单独调整该色值。
背景 / Alpha 白底、无 alpha 通道 禁止透明背景。带 alpha 的 TIFF 会被不少期刊系统判为不合规（排版时透明区可能被填成黑色，深色文字直接消失）。显式设 bg = "white"，并确认输出未写入 alpha。
压缩 LZW 无压缩体积过大易触发上传上限；JPEG 压缩属有损，分辨率事实上被打折。
图层 已拼合（flattened） R 输出的 TIFF 天然是单层位图，不存在此问题；若经 Photoshop 加工，务必拼合后再存。

4.3　光栅化的代价：文字不可编辑

权衡

TIFF 是位图，不存在字体嵌入问题（字形已经是像素），这消除了字体缺失的风险；但反过来，文字被永久栅格化、不可编辑。Nature 等刊要求图内文字可由编辑部修改（改字号、改单位、统一术语），此时位图无法满足——应同时提供矢量版本（PDF/EPS），或在图中不放置需要编辑的文字。

实务建议：位图用于终稿提交，矢量版留作返修与校样使用。两版必须同源（同一段 ggplot 代码 + 同一 family），否则校样阶段的修改会与已提交位图脱节。

  -profile "sRGB.icc" \

5正确实现的技术路线

要让"预览 = 导出"，需要同时满足两个条件：同一套排版引擎 + 同一组物理参数。前者由 ragg 提供，后者由你的代码提供。缺一不可。

5.1　为什么是 ragg 而不是 grDevices::tiff()

表 5-1　两种 TIFF 设备的关键差异
维度ragg::agg_tiff()grDevices::tiff()
文本排版systemfonts + textshaping 引擎，与 agg_png 完全同源；OpenType 特性（连字、字距调整）一致依赖系统图形栈（Windows 上 GDI / cairo 视构建而定），与屏幕设备的字形处理路径不同
抗锯齿Agg 自带高质量抗锯齿，屏幕/输出表现一致依赖底层后端，跨平台差异明显，细线易被"糊"成灰线

速度较快（多线程渲染）较慢
关键机制

agg_png() 与 agg_tiff() 共用同一套 text shaping 引擎（systemfonts 做字体匹配、textshaping 做断行与字形定位）。因此「用 PNG 预览、用 TIFF 出稿」时，字形、字宽、换行点完全同源——这才是预览可信的技术前提。换成一个用 cairo、一个用 Agg，就永远校不准。

5.2　最小可用的出图函数

把单位换算、字体、背景、压缩四件事封装进一个函数，从根上消除"每张图参数都不一样"的问题：

library(ggplot2)
library(ragg)

# pt -> mm：ggplot2 导出的常量，.pt = 72.27/25.4 = 2.845276
# 用于 geom_text(size=)、annotate(size=)、linewidth= 等以 mm 为单位的参数
pt_mm <- function(pt) pt / .pt

# 统一的论文主题：字号 pt，线宽 pt（经 pt_mm 转 mm）
theme_paper <- function(base_size = 7, family = "Arial") {
  theme_classic(base_size = base_size, base_family = family) +
    theme(
      axis.line    = element_line(linewidth = pt_mm(0.5),
                                 colour = "black", lineend = "square"),
      axis.ticks   = element_line(linewidth = pt_mm(0.5),
                                 colour = "black"),
      axis.text    = element_text(size = base_size, colour = "black"),
      axis.title   = element_text(size = base_size),
      legend.title = element_text(size = base_size),
      legend.text  = element_text(size = base_size - 1),
      legend.key.size = unit(3, "mm"),
      plot.title   = element_blank(),   # 图题放正文图注，不进图
      panel.grid   = element_blank()
    )
}

# 只做一件事：按 mm 出 TIFF + LZW，白底，无 alpha
save_paper_tiff <- function(plot, file,
                             width_mm, height_mm,
                             dpi = 600) {
  ggsave(
    filename    = file,
    plot        = plot,
    device      = ragg::agg_tiff,
    width       = width_mm,
    height      = height_mm,
    units       = "mm",        # 强制 mm，杜绝 inch 默认值
    dpi         = dpi,
    bg          = "white",      # 白底，禁止 transparent
    compression = "lzw"        # 无损压缩
  )
  invisible(file)
}

用法

p <- ggplot(df, aes(x, y)) +
  geom_line(linewidth = pt_mm(1), colour = "#1f4e79") +
  geom_point(size = 1.2) +          # 点直径单位是 mm，无需换算
  annotate("text", x = 2, y = 5,
           label = "P < 0.001",
           size = pt_mm(7), family = "Arial") +
  labs(x = "Time (h)", y = "Concentration (mM)") +
  theme_paper(7)

save_paper_tiff(p, "Fig1.tif", width_mm = 90, height_mm = 70,
                dpi = 600)

5.3　预览方案：把 PNG 按物理尺寸投回屏幕

核心思路：用与出稿完全相同的画布尺寸渲染 PNG，再按物理单位（mm）交给 grid.raster()。此时屏幕上的像素密度变了，但"字号占画布的比例"没变——这正是印刷时的比例。

library(grid)

preview_paper <- function(plot, width_mm, height_mm, dpi = 600) {
  tf <- tempfile(fileext = ".png")

  # 与 agg_tiff 同引擎、同物理尺寸 —— 版面与出稿完全一致
  ggsave(tf, plot,
         device = ragg::agg_png,
         width = width_mm, height = height_mm,
         units = "mm", dpi = dpi, bg = "white")

  img <- png::readPNG(tf)

  # 按物理尺寸绘制，而非按像素 —— 这是"等比例"的关键
  grid.newpage()
  grid.raster(img,
              width  = unit(width_mm,  "mm"),
              height = unit(height_mm, "mm"),
              interpolate = FALSE)
}

preview_paper(p, 90, 70)
性能提示

预览时 dpi 可降到 150：因为字号以 pt、画布以 mm 声明，dpi 只影响像素密度，不影响版面，降 dpi 能显著加快渲染与 grid.raster 的刷新速度，而字号占比、换行位置、留白比例完全不变。若需要逐像素检查抗锯齿与细线，再用 dpi = 600 跑一次终检。

显示设备也要够大

grid.raster 按 90 mm × 70 mm 绘制，若当前图形设备（Plots 面板）本身小于该尺寸，图会被裁切或强制缩放。预览前把设备放大到足以容纳目标尺寸（例如 dev.new(width = 6, height = 5, noRStudioGD = TRUE)），或使用独立的图形窗口、放大查看。

5.4　中文字体：注册一次，全程显式引用

ragg 通过 systemfonts 访问系统字体，中文不需要 showtext，但必须注册并显式指定 family，否则可能回退到不含中文字形的字体：

systemfonts::system_fonts() |>
  subset(grepl("Han|Hei|Song|YaHei", family))

# 2) 注册中文字体（文件名因系统而异，按上一步实际路径填写）
systemfonts::register_font(
  name  = "CJK",
  plain = "C:/Windows/Fonts/msyh.ttc",
  bold  = "C:/Windows/Fonts/msyhbd.ttc"
)

# 3) 在主题里显式使用；不要调用 showtext_auto()
theme_paper(9, family = "CJK")
禁用 showtext

不要在你的出图脚本里加载 showtext，也不要调用 showtext_auto()。showtext 会接管文本渲染并维护独立的字体注册表，与 ragg 的 systemfonts 路径冲突；两者共存时，预览与导出可能走不同分支，字形与字宽重新分叉，前面的所有努力全部作废。若历史脚本里已有 showtext，出图前执行 showtext_auto(FALSE) 并卸载。

5.5　出图后自校验：把"看起来对"变成"算出来对"

check_tiff <- function(file, width_mm, height_mm, dpi) {
  info <- magick::image_info(magick::image_read(file))

  exp_w <- round(width_mm  / 25.4 * dpi)
  exp_h <- round(height_mm / 25.4 * dpi)

  cat(sprintf("期望 %d x %d px | 实际 %d x %d px\n",
              exp_w, exp_h, info$width, info$height))
  if (abs(info$width - exp_w) > 1 ||
      abs(info$height - exp_h) > 1)
    warning("像素尺寸不符：units/dpi 可能被设备忽略")

  cat(sprintf("色彩空间: %s | alpha: %s\n",
              info$colorspace,
              ifelse(grepl("TRUE", info$matte),
                     "有（不合规）", "无")))
  cat(sprintf("文件大小: %.1f MB\n", info$filesize / 1024^2))
}

check_tiff("Fig1.tif", 90, 70, 600)

这一步的价值在于机器可判：尺寸差 1 px 以上就警告，alpha 存在就报错。人是看不出 4488 px 和 4520 px 的差别的，脚本可以。

8常见错误 → 正确写法

每组按「错误代码 → 错误后果 → 正确代码」排列，代码可直接复制运行。这里列的 8 组覆盖了绝大多数"预览与导出不一致"的实际案例。

01裸调用 ggsave("fig.tif")
错误代码 
ggsave("fig.tif")
错误后果

三个关键参数全部走默认：尺寸 7 × 5 inch（即 177.8 × 127 mm）、分辨率 300 dpi、设备由扩展名推断（.tif 走 grDevices::tiff()）。对 89 mm 单栏来说宽度超出一倍，对 190 mm 双栏又窄了 12 mm；同时字体走系统默认路径，与预览不同源。图"生成成功了"是最危险的信号——它什么都没告诉你。

正确代码 
ggsave(
  "fig.tif", plot = p,
  device      = ragg::agg_tiff,
  width       = 89, height = 120, units = "mm",
  dpi         = 600,
  bg          = "white",
  compression = "lzw"
)
02geom_text(size = 8) 以为是 8 pt
错误代码 
geom_text(aes(label = lab), size = 8)
错误后果

size 的单位是 mm，不是 pt。8 mm 字高 ≈ 22.76 pt，比预期的 8 pt 大 2.8 倍。后果是标注压住数据点、互相重叠、溢出画布；更麻烦的是它不受 theme(base_size=) 控制，调主题毫无效果，作者往往在这里卡很久。注意 geom_point(size=) 也是 mm（点直径），但那个单位是符合直觉的——同名字段、两种语义，正是陷阱所在。

正确代码 
# .pt 是 ggplot2 导出的常量：72.27 / 25.4 = 2.845276（pt per mm）
geom_text(aes(label = lab),
          size = 8 / .pt,
          family = "Arial")

等价写法：size = pt_mm(8)。团队里固定用其中一种，别混。

03linewidth = 1 以为是 1 pt
错误代码 
geom_line(linewidth = 1)
theme(axis.line = element_line(linewidth = 1))
错误后果

linewidth 单位为 mm（ggplot2 ≥ 3.4）。linewidth = 1 = 1 mm ≈ 2.83 pt，接近期望的三倍，直接越过多数期刊 1.5 pt 的上限，整张图显得"糊、重、业余"。反向错误同样常见：把 0.25 pt 写成 0.25（= 0.71 pt）看似无害，但若再往下写成 0.1（= 0.28 pt），在 300 dpi 下已接近抗锯齿不可分辨的边界。

正确代码 
geom_line(linewidth = 1 / .pt)                       # 1 pt 数据线
theme(axis.line  = element_line(linewidth = 0.5 / .pt),  # 0.5 pt 轴线
      axis.ticks = element_line(linewidth = 0.5 / .pt),
      lineend = "square")
04element_text(size = 8) 与 geom_text(size = 8) 混用
错误代码 
theme(axis.text = element_text(size = 8))   # 8 pt
geom_text(..., size = 8)                      # 8 mm！
错误后果

作者以为"两个 8 一样大"，实际上轴标签是 8 pt、图内标注是 22.76 pt，相差 2.8 倍。视觉上标注像标题一样抢眼，整张图失去层次；审稿人常批注 "text sizes are inconsistent"。这类错误特别隐蔽，因为代码看起来完全对称、完全"合理"。

正确代码 
# 用一个常量表达"同一个字号"，两边各自转换
FS_LABEL <- 8   # 语义单位：pt

theme(axis.text = element_text(size = FS_LABEL))          # pt 直传
geom_text(..., size = FS_LABEL / .pt, family = "Arial")  # 转 mm
05不指定字体，任由设备替换
错误代码 
ggplot(df, aes(x, y)) + geom_point()    # 没写 family
# 屏幕上 = Arial；pdf() 里 = Helvetica；ragg 里 = systemfonts 匹配结果
错误后果

sans 是逻辑别名，由具体设备解析。换设备即换字形、即换字宽，而 ggplot 用字体度量计算文本包围盒（决定轴标签是否旋转、图例是否换行）——版面会重排。表现是：屏幕上一行的标签，导出后变两行并溢出；或图例被挤到图外。PDF 设备更极端：默认只认 Type1 标准字体，不嵌入系统字体，别人打开时直接替换。

正确代码 
library(systemfonts)
FONT <- "Arial"
stopifnot(nzchar(match_font(FONT)$path))   # 出图前断言字体存在

theme_paper(7, family = FONT)   # 由 base_family 贯穿全图

另：不要为了显示中文而加载 showtext，它会与 ragg 的字体路径冲突。中文用 register_font() 注册后显式引用。

06bg = "transparent" 透明背景
错误代码 
ggsave("fig.tif", p, bg = "transparent")
# 或 theme(plot.background = element_rect(fill = NA, colour = NA))
错误后果

输出写入 alpha 通道，被多数期刊系统判为不合规。更实际的风险是：排版软件把透明区填成黑色，深色文字与轴线直接消失；或在 Word/PDF 里变成棋盘格。屏幕预览时因底色为白，你根本发现不了——这是"预览骗人"的典型案例之一。

正确代码 
ggsave("fig.tif", p,
       device = ragg::agg_tiff,
       bg     = "white",        # 白底，不写 transparent
       compression = "lzw")

# 出图后确认无 alpha（见 §5.5 check_tiff）
07dpi = 600 但 width 用默认 7 inch
错误代码 
ggsave("fig.tif", p, dpi = 600)   # 只设 dpi，尺寸走默认
错误后果

得到 7 × 5 inch = 177.8 × 127 mm、4200 × 3000 px。作者看到"600 dpi"就放心了，但物理尺寸对单栏超宽一倍；投稿系统按 89 mm 栏宽排版时会把它缩到一半，于是原本 7 pt 的字变成 3.5 pt——"分辨率 600 dpi 却不可读"的组合故障。dpi 与物理尺寸是两个正交维度，改一个救不了另一个。

正确代码 
ggsave("fig.tif", p,
       device = ragg::agg_tiff,
       width  = 89, height = 120,   # 期刊栏宽
       units  = "mm",                  # 关键：单位显式
       dpi    = 600)                   # 2102 × 2835 px
08忘了 units，把 mm 数值当 inch 传
错误代码 
ggsave("fig.tif", p,
       device = ragg::agg_tiff,
       width = 190, height = 250,   # 缺 units = "mm"
       dpi = 600)
错误后果

默认单位是 inch，于是画布变成 190 × 250 inch = 4826 × 6350 mm，即 4.8 × 6.4 米。像素数 114000 × 150000，约 51 GB 未压缩内存——R 会先卡死、然后报 cannot allocate vector，或者更糟：顺利生成一个 2 GB 的怪物文件，上传时被拒。这个错误的特点是一眼看不出来，因为数字本身"完全正确"。

正确代码 
# 把 units 写进封装函数，永不手写 ggsave
save_paper_tiff <- function(plot, file, width_mm, height_mm, dpi) {
  ggsave(file, plot,
         device = ragg::agg_tiff,
         width = width_mm, height = height_mm,
         units = "mm", dpi = dpi, bg = "white",
         compression = "lzw")
}

save_paper_tiff(p, "fig.tif", 190, 250, 600)

函数名里带 _mm 是刻意的：让参数语义在调用处可见，降低传错单位的概率。

像素取整的实际行为

ragg 1.3.2 对 mm ÷ 25.4 × dpi 的非整数结果采用向下取整，不是四舍五入。例如 89 mm @600 dpi 理论值 2102.36 px，实际输出 2102 px，反算物理尺寸为 88.985 mm。误差约 0.015 mm，远小于期刊容差，但你要知道它来自取整，而不是配置写错了。校验时应允许 < 0.1 mm 的这类偏差。

9.3　预览与最终 TIFF 的逐像素比对

比对方法：用同一 spec 先输出一张 compression = "none" 的 TIFF，用 base R readBin() 直接解析 IFD 的 StripOffsets / StripByteCounts / RowsPerStrip 读出原始 RGB 字节；再用同一 spec 输出 PNG 并 png::readPNG() 读出预览像素，两者逐像素求差。因为 LZW 是无损压缩，"未压缩 TIFF 的像素"就等于"LZW TIFF 解码后的像素"，所以这一步构成严格证明，而不是同义反复。

实测抓到的真凶：随机图层

第一次比对时，柱状图有 9 000 个像素（0.30%）不一致，最大通道差达 255，而折线图完全一致。原因不是渲染，而是 geom_jitter()：它每次绘制都会重新抽一次随机偏移，预览抽一次、保存再抽一次，两张图里的散点自然落位不同。

这类问题在设备、单位、字体全部正确时依然会出现，极难自查。修复只需把种子固定到 position 上——注意 geom_jitter() 本身不接受 seed 参数，写了会被静默忽略：

# 错误：seed 被忽略，预览与输出仍会不同
geom_jitter(width = 0.08, seed = 42)

# 正确：种子交给 position_jitter
geom_point(position = position_jitter(width = 0.08, height = 0, seed = 42))

更稳妥的科研写法是预先算好抖动坐标存进数据框再 geom_point()，这样图形完全确定，换机器、换设备都复现得出来。

其他实测发现
  • patchwork 与 ggplot2 4.0 不兼容：patchwork & theme(...) 会报 Can't find method for generic &(e1, e2)。改为先给每个子图 + theme_pub(spec)，再用 | / / 组合。
  • 中文字体：用 systemfonts::register_font() 把 simsun.ttc 注册为别名后，600 dpi 下中文无缺字、无豆腐块；全程未启用 showtext。
  • 退出码：本验证容器中，R 进程在加载 cli 包后于退出清理阶段触发段错误（exit 139），可用 Rscript -e "requireNamespace('cli')" 独立复现，与绘图逻辑无关；所有文件均已完整落盘且校验通过。在常规 RStudio / 终端环境不会出现。
